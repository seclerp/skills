# Directory Mapping

Full test-type → `compiler/testData/...` mapping used by `kt-add-test`. All paths are **project-root-relative**
(e.g. `compiler/testData/codegen/box/...`), regardless of which worktree/clone invokes the skill.

## Primary categories

| Snippet intent | Target directory | Notes |
|---|---|---|
| Runs and returns a checkable result, backend-agnostic | `compiler/testData/codegen/box/<topic>/` | Body becomes `fun box(): String`, returning `"OK"` on success. This is the default for "does this code run/behave correctly" asks. |
| Runs, but only makes sense on (or is only tested on) one backend | `compiler/testData/codegen/boxJvm/` for JVM-only; sibling folders (`boxWasmJsInterop/`, etc.) for other single-backend cases | **Enforced by `PureJvmCodegenBoxTestChecker`**: any test under `compiler/testData/codegen/*` whose *only* `TARGET_BACKEND` is JVM/JVM_IR must live in `codegen/boxJvm`, not `codegen/box` — the checker fails the test otherwise. |
| Should or shouldn't report a diagnostic (error/warning) | `compiler/testData/diagnostics/tests/<topic>/` | Topic subfolder chosen from the list below (mirrors `compiler/testData/diagnostics/resolve/` topic conventions documented in `AGENTS.md`). |
| Verifies generated IR shape/structure | `compiler/testData/ir/irText/<topic>/` | Companion `.ir.txt` / `.kt.txt` files are auto-generated by the test run — never hand-written. |
| Verifies exact bytecode shape (instructions/class layout) | `compiler/testData/codegen/bytecodeListing/` or `compiler/testData/codegen/bytecodeText/` | Rare; only when the ask is explicitly about bytecode, not runtime behavior. |
| Multi-file / multi-module / Java interop variant of any of the above | Same target directory as the base category, using `// FILE:`/`// MODULE:` directives inside one `.kt` file (or an accompanying `.java` file) | Splitting doesn't change the directory — only the in-file structure (see `reference/directives.md`). |

## Diagnostics topic subfolders (`compiler/testData/diagnostics/tests/<topic>/`)

Pick the topic that matches the snippet's subject; if genuinely nothing fits, create a new topic folder using the same
lowerCamelCase naming style. From `compiler/fir/analysis-tests/AGENTS.md`:

- `annotations/`, `arguments/`, `arrays/` — basic language constructs
- `builtins/`, `stdlib/` — standard library interactions
- `callResolution/` — call resolution scenarios (overloads, invoke, SAM, operators)
- `cfa/`, `cfg/` — control flow analysis and graphs
- `checkers/`, `extraCheckers/`, `diagnostics/` — diagnostic-focused tests
- `collectionLiterals/`, `constructors/`, `constVal/` — specific constructs
- `contextParameters/`, `contextSensitiveResolutionUsingExpectedType/` — context-dependent resolution
- `contracts/` — Kotlin contracts
- `delegates/`, `destructuring/` — delegation and destructuring
- `exhaustiveness/` — exhaustive when/sealed checks
- `expresssions/` (note: misspelled in repo — keep the misspelling for consistency), `fromBuilder/` — expression-level tests
- `headerMode/` — header/expect declarations
- `inference/` — type inference
- `inlineClasses/`, `innerClasses/`, `localClasses/` — class variants
- `j+k/` — Java-Kotlin interop
- `multifile/` — multi-file tests (using `// FILE:` directive)
- `multiplatform/` — multiplatform expect/actual
- `nestedTypeAliases/`, `typeArguments/`, `typeParameters/`, `types/` — type system
- `overloadResolution/`, `overrides/` — overloading and overriding
- `problems/` — regression/bug-repro scenarios (a good default for "reproduce this KT-XXXXX bug" diagnostics tests)
- `properties/`, `propertyVsField/` — property resolution
- `qualifiers/`, `references/` — qualified access and references
- `returnInExpressionBodies/` — return in expression body functions
- `samConstructors/`, `samConversions/` — SAM conversion tests
- `scopes/`, `visibility/` — scoping and visibility
- `scripts/` — Kotlin scripting
- `smartcasts/` — smart cast tests
- `suppress/` — `@Suppress` annotation tests
- `unqualifiedEnum/` — unqualified enum access
- `vfir/` — virtual FIR tests
- `withAllowedKotlinPackage/` — tests allowing the `kotlin` package

## Hard exclusions — never place a new test here

| Location | Reason | Redirect to |
|---|---|---|
| `js/js.translator/testData/**` (`box/`, `lineNumber/`, `typescript-export/`, etc.) | Kotlin/JS-specific box/lineNumber/typescript-export infrastructure — a completely separate test system from the backend-agnostic compiler tests (`js/js.tests/ReadMe.md`). | `compiler/testData/codegen/box/<topic>/` (backend-agnostic); if truly JS-only, that's a signal this request belongs to a different, JS-specific skill/workflow, not `kt-add-test`. |
| `native/native.tests/**` | Kotlin/Native has its own generator/test infra, out of this skill's scope. | Not handled by this skill; tell the user to use Kotlin/Native's own test tooling. |
| `wasm/wasm.tests/**` | Kotlin/Wasm has its own generator/test infra, out of this skill's scope. | Not handled by this skill; tell the user to use Kotlin/Wasm's own test tooling. |
| Analysis API tests (`analysis/**`) | Has dedicated per-module codebase tests and its own skill (`analysis-api-mark-internal-apis`). | Point the user to that skill instead. |
| Gradle plugin tests | Separate test infra entirely unrelated to `compiler/testData`. | Out of scope for this skill. |

If the user explicitly asks for one of these locations, **refuse that specific location**, explain why (in one sentence,
citing the reason above), and propose the correct `compiler/testData/...` equivalent instead — don't silently redirect
without saying so.
